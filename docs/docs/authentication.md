# Authentication

Authentication in LifeXOS is managed entirely by Supabase Auth (GoTrue). This provides secure JWT-based session management, password hashing, and OAuth provider integrations.

## Core Flow
1. **Sign Up / Registration**: The user registers via the client using `@supabase/supabase-js`.
2. **Database Triggers**: 
   - Upon successful creation in the `auth.users` schema, two PostgreSQL triggers run instantly:
     - `on_auth_user_created` calls `handle_new_user()` to generate the `public.user_data` JSONB row.
     - `on_auth_user_created_ai_profile` calls `handle_new_user_ai_profile()` to generate the `public.user_ai_profiles` row.
3. **Sign In**: The client receives an access token (JWT) and a refresh token. These are stored locally.
4. **Session Management**: The `@supabase/supabase-js` client handles token refresh automatically.

## Integration with Edge Functions
Edge functions in LifeXOS that require authentication explicitly set `verify_jwt = false` in `supabase/config.toml` so they can handle CORS `OPTIONS` preflight checks. 
Instead, they manually authenticate requests using the shared `auth.ts` module:
```typescript
// Example from Edge Functions
const user = await getAuthUser(req);
if (!user) return unauthorizedResponse(corsHeaders);
```
This extracts the `Authorization` header, passes it to the Supabase client, and retrieves the validated user identity from `auth.users`.

## Account Deletion
Because the database tables are strictly linked to `auth.users(id)` via `ON DELETE CASCADE`:
- Deleting an account through the `delete-account` Edge Function immediately scrubs the user's data from `public.user_data`, `public.user_ai_profiles`, `public.ai_profile_versions`, `public.user_audit_logs`, and `public.user_feedbacks`.
- The user is completely removed from the system.

## Row Level Security
The JWT generated by Supabase Auth contains the `sub` claim mapping to `auth.uid()`. All database requests verify this identifier against the `user_id` column of the tables via RLS policies.
